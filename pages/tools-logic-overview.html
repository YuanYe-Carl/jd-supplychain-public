三个决策工具到底在算什么

用不绕弯子的话，讲清楚 Free Goods BBCC 费用仿真、11RDC/62仓备货仓比、消费者订单履约判定这三个工具各自的 数据来源、核心判断规则和输出结果，方便在用之前先明白它凭什么给出这个数。

三个工具都是确定性计算，不使用生成式模型推算库存与成本；相同输入必然得到相同结果。

TOOL 01

Free Goods BBCC 费用仿真

它回答一个问题：HC 赠品如果不再全部走京东 11 大仓直送，而是先囤到「B 仓」再分发到各个城市，一年要多花多少钱、货到得慢多少天。

用了哪些数据

数据来源在算法里的作用
赠品 SKU 清单（箱规、首件 / 续件 / 整箱出库费）计算出库费
FY2526 历史月度发货量（数量、体积、重量）作为未来货量的推算基础
近 90 日各收货地商品件数决定每个城市分到多少货
BBCC 新报价表（13 个 B 仓地址 + 运输报价）计算运输费与时效
11 区域对应关系没有可用线路时收敛回 11 大仓

底层逻辑六步

01

把货分到城市

拿每个 SKU 的历史月发货量，按「近 90 日各城市销量占比」摊到各个 C 城市。

占比之和不到 100% 的部分算作未建模，单独列入异常清单，不会硬凑成 100%。

02

判断每个城市怎么送

北京、上海、广州等 11 个 RDC 城市默认宝洁直送，不产生 BBCC 费用；其他城市走 B 仓中转。每个城市的走法都可以在界面上手工覆盖。

03

选哪个 B 仓（核心判断）

对每个 C 城市，把所有启用的 B 仓各试一遍，算出全年运输总费用，谁最便宜选谁。

若手工指定的 B 仓没报价、或所有 B 仓都没有到该城市的线路，则回退成 11 大仓代发，费用记 0，并明确写进异常清单。

04

按调拨频次拆任务

用中国工作日历（含法定节假日调休）算出全年可调拨日，再按选定频次（每工作日 / 每周 1–5 次）得出每月任务数。

月货量 ÷ 任务数 = 单次任务量。发得越频繁，单次的量越小，单位成本越吃亏。

05

算钱（四类费用）

运输费：计费重量取 max(实际重量, 体积×200)，抛货按体积重算，再按 ≤1000kg / >1000kg 两档单价。

出库费：能凑整箱的按整箱费；剩下散支只收一笔最贵的首件费，其余按续件费。

保费：货量 × 货值 3 元 × 万分之 5，只对走 BBCC 的货收。PG→B 运输：月趟数 × 单趟费用。

06

算时效

走 BBCC 为 PG→B 天数 + B-C 报价时效（报价写 3D2359 按 4 天算）；直送与回退使用 11 大仓直送时效。

全国平均按货量加权；直送的货计入时效，但完全不计入成本。

计费重量 = max(实际重量 kg, 体积 m³ × 200)  |  单次任务量 = 月货量 ÷ 当月任务数
折扣比例可调 默认 PG→B 运输 100%、B-C 运输 60%、整箱与散支出库 50%、存储 50%、保费 100%，全部可在界面上修改后重新测算。

实现了什么功能

  • 本机网页界面，可调 13 个 B 仓的启用状态、月趟数、单趟费用、调拨频次、折扣比例与逐城市路由
  • 一次仿真同时给出全年增量费用拆解 + 全国加权时效 + BBCC 覆盖率
  • 导出 Excel：城市路由与时效、各 B 仓候选成本对比、月度任务明细、PG→B 容量校验、异常清单
异常不掩盖 没有报价的线路、销量未映射完整的 SKU、平均每次任务不足 1 支的城市，都会单独列出来交给人判断，而不是自动填一个默认值糊弄过去。
TOOL 02

11RDC / 62仓备货仓比查询

它回答：我这批货（某个品牌 / 类目 / SKU 清单）要备到全国仓库里，每个仓该放百分之多少。 并且同时给出两套答案——只铺 11 个大仓，和铺 62 个直送仓。

用了哪些数据

数据来源在算法里的作用
JD 库存大表（自动取最新切片）提供 SKU、品牌、三级类目、采购价，以及近 90 日各配送中心收货件数
宝洁直送明细确定哪 62 个是普通 C 仓，以及每个仓的城市与仓型
11RDC 映射表把杂乱的配送中心名字对应到 11 大仓
城市经纬度库计算球面距离，用于就近归仓

底层逻辑四步

01

先把仓库名字理清楚

库存大表里的配送中心名字很乱——「上海FDC」「北京大商超」「徐州FDC配送中心」「南通本地仓中心」。先用别名表和后缀剥离，统一成标准城市名。

02

每个配送中心归到哪个 62 仓（核心判断）

如果它本身就是 62 个普通 C 仓之一，归给自己；否则用经纬度算球面距离，找地理上最近的那个普通 C 仓城市。

03

每个配送中心归到哪个 11RDC

优先查映射表；表里没有就反推——看这个配送中心下的 SKU 里哪个 RDC 出现次数最多，就归给谁。

04

算比例

用「近 90 日收货地商品件数」当需求权重，把每个配送中心的销量累加到它对应的 11RDC 和 62 仓上，再各自除以总量。

某仓仓比 = 该仓归集的 90 日销量 ÷ 全部选中 SKU 的 90 日销量

一个值得说的设计：边界仓标记

按「最近距离」归仓有个隐患——有些城市夹在两个仓中间，归给谁都说得通，但结果会差很多。

触发条件（满足任一）

标记为「边界」

最近仓与第二近仓的距离差 < 150 公里；或最近距离 ÷ 第二近距离 > 0.8。

配套输出

第二候选仓与距离

提醒你这行归属不稳，业务上换个仓也合理，别盲信这个数。

实现了什么功能

  • 网页查询（发布在 GitHub Pages），按品牌 / 一二三级类目 / SKU 清单 / 采购价是否为 0 筛选
  • 同时输出 11RDC 方案与 62 仓方案两套比例，可切换「11 仓备货只发 11 城」或「62 仓发全国」
  • 可选择只看某类仓（11RDC / 普通C仓 / 城市仓 / 轻货仓）
  • 导出 Excel，含每个原始配送中心的完整映射轨迹（归到哪、距离多远、第二候选是谁、是否边界、置信度）
  • 每天自动检查库存切片是否更新，有更新就重建
两个容易被忽略的口径

轻货仓默认不计入仓比——它走另一套逻辑，混进来会扭曲比例；但排除掉的销量会单独列出，不是偷偷丢掉。

数据是加密发布的——含内部销量，模型用 AES-GCM 加密、PBKDF2 迭代 60 万次派生密钥，页面需输入密码才能解开，原始数据不会明文进入 GitHub。

宁可报错也不糊弄 构建时有几道硬校验，不满足直接中断：普通 C 仓必须正好 62 个；同一城市不能有两个普通 C 仓；有销量的配送中心必须能找到 11RDC 与 62 仓归属。 这样保证比例合计一定是 100%，不会有货凭空消失在某个没映射上的仓里。
TOOL 03

消费者订单履约判定与 Upcharge

它回答：一个消费者下单后，京东会从哪几个仓发货、算不算拆单、宝洁要为此多付多少钱。

三个核心概念

FULFILLMENT FROM

履约 from

发货点，粒度是「配送中心 + 库房名称」。同一配送中心下两个库房算两个 from。

FULFILLMENT TO

履约 to

消费者城市收敛后的应发货城市；非直送城市归到所属 11 区域核心城市。

NETWORK

网络（仓型）

普通 C 仓 / 轻货仓 / 城市仓，决定计费方式与覆盖范围。

一个容易搞混的点 仓库能覆盖某个城市 ≠ 它是本地仓。是不是「本地」，永远比较物理城市与应发货城市。

第一层判断：这是什么订单

同时包含至少一个主品和一个赠品 → 绑赠订单
非绑赠，且全部 SKU 的一级类目唯一 → 同品类订单
非绑赠，且存在多个一级类目 → 跨品类订单
任一 SKU 一级类目缺失 → 保守按跨品类处理
为什么先判类型 因为业务上绑赠和同品类订单不希望轻易拆单——赠品和主品分开发，消费者体验差。

第二层判断：选发货仓

  • 绑赠 / 同品类订单：先搜索「同区 + 单个仓 + 整单发完」的方案。只要存在可行解就在其中选择，哪怕本地有部分库存也不拆单
  • 跨品类订单，或上面找不到解：进入通用分仓策略

通用分仓的排序优先级，依次比较：

本地承担量最大→ 覆盖层级最优→ 总 upcharge 最低→ from 数最少→ 固定 from 顺序
注意第一顺位不是成本 先尽量让本地仓多发，再谈省钱。覆盖层级从优到劣为：原覆盖关系 → 轻货仓跨区兜底 → 普通 C 仓全国平行兜底。

Upcharge 怎么算

基础仓（第一个 from）不收费，费用只来自「多出来的仓」。

场景费用
每个新增普通 C 仓生产费 1.5 元
每个新增轻货仓 / 城市仓生产费 1 元 + 配送费 2 元
上一行，但订单里有本地普通 C 仓生产费抵减 0.3 元 → 合计 2.7 元
同区跨城配送0.8 元，整单只收一次
跨区配送每个跨区子单 3 元，累计
本地普通 C 仓 + 跨区拆单每个跨区子单另加 4 元基础配送费
一条容易漏的规则 跨网配送费 3 元与普通地理配送费取高、不叠加，不会两笔都收。

输出三组标签

地理

本地同城 / 同区跨城 / 跨区

按所有 from 的物理城市与应发货城市比较得出。

网络

同网 / 跨网

全部 from 仓型相同为同网，否则为跨网。

仓级

同仓 / 跨仓

一个 from 为同仓，多个为跨仓。严格按「配送中心 + 库房名称」识别。

三者组合即为发货模式，例如 本地同城发货 / 同网 / 同仓。

实现了什么功能

  1. 真实订单批量判定——从 Excel 粘贴「订单号 / 收货城市 / JD码 / 数量」四列，逐单算发货方式与 upcharge
  2. 绑赠机制模拟——还没有真实订单时，用主品的近 90 日收货地商品件数模拟全国城市分布，推算机制铺开后各发货模式占比与平均每单 upcharge
  3. 网页配置——城市收敛映射、库存切片选择、各项费率均可在界面修改，保存后立即生效
  4. 输出各模式比例、平均每单 upcharge、每 1000 单 upcharge
分仓求解用的是精确搜索，不是贪心 代码里用带缓存的递归穷举所有可行仓组合（本质是集合覆盖问题），保证找到真正的最优解。 贪心在这里会出错——比如某个仓看着能发最多，但选了它反而逼出更多跨区子单。
库存口径很保守

按可订购库存 > 0使用，负数按 0 处理。

库存表没有库房名称时，靠RDC + 配送中心 + 品类唯一连接直送明细，一旦出现一对多就停止，绝不复制库存凑数。

多个订单之间互不影响，不按顺序扣减库存——目的是分析这类订单典型会怎么发，而非模拟某一天的真实履约顺序。

COMPARISON

三个工具横向对比

同样是仓网相关，但回答的问题、时间尺度和输出粒度完全不同。

BBCC 费用仿真 备货仓比查询 履约判定与 Upcharge
回答的问题 改走 B 仓会多花多少钱 每个仓该放多少货 这一单会怎么发、多付多少
决策层级 网络设计（要不要建 B 仓） 库存布局（货放哪） 单笔履约（怎么发出去）
时间尺度 全财年 近 90 日滚动 单笔订单瞬时
核心权重 历史发货量 × 城市销量份额 近 90 日收货地商品件数 实时可订购库存
关键判断 选全年运输费最低的 B 仓 球面距离最近的普通 C 仓 本地优先 → 覆盖层级 → 成本
主要输出 增量成本 + 加权时效 两套备货比例 发货模式 + upcharge
兜底机制 回退 11R 代发，费用记 0 有销量必须有归属，否则报错 库存不足则标记无法履约
DESIGN PRINCIPLES

三个工具共同遵守的原则

01 · DETERMINISTIC

确定性计算

全部是规则与公式，不用生成式模型推算库存或成本。相同输入必然得到相同结果，算出来的数可以直接拿去对账。

02 · EXPLICIT

异常显式暴露

没报价的线路、未映射的销量、库存对不上的情况，一律单独列出交给人判断，而不是填默认值掩盖过去。

03 · FAIL FAST

宁可报错不糊弄

关键主数据不满足前提（如普通 C 仓不是 62 个、库房一对多）时直接中断，避免用错误的基础数据算出一个看起来合理的结果。

为什么强调这三点 供应链决策的数字一旦进入汇报或谈判，就很难再追溯它是怎么来的。 与其给一个「大概对」的漂亮结果，不如在数据不足时明确说不知道——这样每个数字才敢拿出去用。
