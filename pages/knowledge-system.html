02 / Knowledge Journey

一条知识如何完成旅程

六层结构不是六套彼此分开的东西，而是一条材料逐渐变得“可找、可懂、可组合、可被程序使用”的成长路径。

01 入口层 · Inbox

先收进来

Word、PPT、Excel、截图、链接、会议结论或一句经验，都可以先放进收集箱。

解决：知识不再只留在个人电脑和聊天记录里。
02 知识层 · Atom / Source

把一件事讲清楚

AI 把长材料拆成“一张知识卡片讲一件事”，同时保留原始来源和贡献者。

解决：以后能单独找到、引用和更新某条知识。
03 导航层 · MOC

放进正确的目录

订单、库存、运输、仓网等主题各有自己的内容地图，告诉新人从哪里开始看。

MOC：就是某个主题的目录页和阅读路线。
04 网络层 · 双链 / 标签

和其他知识连起来

一条库存知识可以连到仓网、履约和费用。人可以顺着关系阅读，AI 也能跨主题寻找关联。

解决：文件不再是一座座孤岛。
05 洞察层 · Insight

从知识中发现规律

把多条事实放在一起，找出矛盾、空白和可验证的新判断，并明确标注置信度。

注意：推理结果和已确认事实分开保存。
06 本体层 · Ontology

提炼成统一业务语言

从大量知识中提取稳定的对象、字段和关系，例如订单、SKU、库存、仓和履约。

结果：团队和 App 开始使用同一套业务词典。
原材料 → 可复用知识 → 知识网络 → 新洞察 → 统一业务口径 → 可落地的业务 App
↻ App 运行中发现的新问题和新规则，会重新进入这条旅程，持续推动知识库更新。
03 / System Components

知识库是怎么构成的

知识内容解决“我们知道什么”，知识库约定解决“如何保持可信”，Agent 解决“如何访问”，本体解决“系统如何理解这个业务世界”。

01 · KNOWLEDGE

知识内容

知识库保存的不只是整理后的结论，也保留它们从哪里来、适用于哪里，以及与其他知识有什么关系。

  • 原始文件、会议结论、截图、链接与业务经验
  • 一张卡片讲清一件事的原子知识
  • 订单、库存、仓网、费用等主题地图
  • 与事实分开保存、等待验证的新洞察
02 · CONVENTIONS

知识库约定

约定不是排版规范，而是整套系统保持可信、可追溯和可持续维护的治理规则。

  • 来源、贡献者、生效时间、适用范围和版本
  • 事实、推断、规则、例外与待确认内容的区分
  • 冲突信息的保留、比较、确认与替代方式
  • 公开内容、内部知识和敏感材料的权限边界
03 · KNOWLEDGE AGENT

知识库 Agent

Agent 是知识系统的 Chat 入口，让成员可以用自然语言检索、理解和串联自己有权限访问的知识。

  • 回答时引用具体知识来源，而不是只给结论
  • 区分已确认事实、推断和仍有冲突的内容
  • 继承 SharePoint 权限，不绕过边界访问敏感知识
  • 帮助新材料和新问题重新进入知识旅程
04 · ONTOLOGY

本体

本体是团队与程序共同认可的业务词典，定义对象、字段、单位、关系和规则边界。

  • 订单、SKU、RDC、配送中心、库存、费用和 KPI
  • JD 码、可订购库存、收货城市等字段口径
  • 订单消耗库存、配送中心属于区域等关系
  • 通过约束减少自由猜测，更早暴露歧义和错误映射
CONFLICT HANDLING

知识冲突怎么处理

系统不为了得到一个流畅答案而悄悄消除冲突。

发现冲突两条知识给出不同口径或结论。
→

→
确认或保留能判断则替代；不能判断则标记并等待确认。
AGENT GUARDRAILS

Agent 能做什么，不能做什么

Agent 负责检索、摘要与解释；确定性业务计算交给 App。

回答必须带来源
事实与推断分开
遵守内容权限
不猜库存与费用
ONTOLOGY EVOLUTION

本体如何持续自我更新

“自我更新”不是 AI 自动改规则，而是新知识与 App 异常不断触发候选变化， 经影响检查和业务确认后，再形成新的本体版本。

01 · SIGNAL

发现变化

新知识、新对象或 App 异常暴露本体缺口。

02 · PROPOSAL

形成候选

识别可能新增或需要调整的定义与关系。

03 · REVIEW

检查影响

比较重复、冲突、适用范围和受影响 App。

04 · CONFIRM

业务确认

负责人确认名称、口径、边界和执行规则。

05 · RELEASE

升级版本

同步人读定义、机器结构和 App 数据契约。

人工确认是本体更新的必要闸门：AI 可以发现候选变化，但不能自行批准公共业务规则。
04 / Operating Architecture

知识库是如何运转的

SharePoint 承载完整知识与受控材料；Agent 提供对话式访问，本体提供结构约束， 业务数据在运行时与规则汇合，最终形成内部 App 与经过审核的公开输出。

PRIVATE · 权限受控

SharePoint 团队知识空间

完整知识与敏感材料集中在团队权限体系内，不因被 Agent 或 App 使用而失去访问边界。

SINGLE KNOWLEDGE SPACE

知识、来源、约定与本体共同存在

原始材料提供证据，知识卡片提供可复用结论，约定负责治理，本体持续从知识中提炼并保留版本。

原始材料 完整知识 敏感内容 知识库约定 主题地图 本体与版本 权限与审计
在权限、来源与版本控制下提供能力↓

05 / Case Study

案例：消费者订单履约工具

这不是让 AI 根据常识猜仓库，而是把知识库里的履约知识、本体约束和最新库存切片， 组合成一个可重复、可解释的确定性模拟引擎。

KNOWLEDGE + DATA + ONTOLOGY

从仓网知识出发，模拟订单路由并计算成本

工具先读取已确认的仓网与费用规则，再结合带时间戳的库存静态切片； 本体负责检查对象、字段、关系和版本，最后由确定性引擎完成候选寻仓、整单拆单与 Upcharge 计算。

① 知识库中的规则

说明“业务应该如何判断”。

  • 仓网覆盖与宝洁直送网络
  • 普通订单与绑赠机制规则
  • 整单、拆单与寻仓优先级
  • Upcharge 费用与特殊仓口径
② 最新业务数据

说明“当前有哪些可用供给”。

  • 订单号、收货城市与 JD 码
  • 配送中心、库房与仓型映射
  • 带时间戳的库存静态切片
  • 机制分析需要的地域权重数据
③ 本体校验与纠错

说明“输入是否符合共同语言”。

  • JD 码、仓、城市与区域能否识别
  • 履约 to / from 是否被正确使用
  • 字段、单位、枚举与关系是否有效
  • 规则范围与本体版本是否一致
三类输入校验后汇合↓

确定性履约引擎

相同输入 → 相同结果
生成候选仓
检查库存可行性
应用路由优先级
判断整单或拆单
计算 Upcharge
输出带依据的模拟结果↓
模拟路由 从哪些履约 from 发货，以及是本地、同区还是跨区。
履约模式 同仓或跨仓、整单或拆单，以及对应子单数量。
费用结果 出库费、配送费和总 Upcharge 的计算结果。
解释与追溯 命中的规则、数据切片时间、本体版本和异常原因。
本体不会替代数据 无法识别对象、映射或规则版本时，系统应阻止计算或明确报错；它不会猜测缺失库存、创造费用规则，也不会把模拟结果宣称为京东 WMS 的实际最终决策。

工具把知识系统中的已确认规则真正落进日常业务判断，也把运行中发现的新问题继续送回知识库。
